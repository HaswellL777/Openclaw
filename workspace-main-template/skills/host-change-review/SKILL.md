# Host Change Review Skill

## Skill identity
- **Name**: `host-change-review`
- **Owner**: `main` agent
- **Purpose**: Review, approve, and execute host-change-request.json from task-runner

## When to use
- task-runner output's `summary.json` has `requires_host_change: true`
- Human asks to review or execute a pending host change request
- Reviewing `/workspace/outputs/<task-id>/host-change-request.json`

## Review workflow

### Step 1: Validate the request

Read the `host-change-request.json` file. Verify:

1. **Required fields present**: task_id, generated_at, requested_host_ops, requires_operator_approval, forbidden_actions, evidence_refs, handoff
2. **Actions are valid**: every `action` in `requested_host_ops` is one of the 8 registered broker actions:
   - `gateway_health`
   - `validate_openclaw_json_candidate`
   - `deploy_openclaw_json_candidate`
   - `snapshot_pre`
   - `snapshot_post`
   - `rollback_prepare`
   - `gateway_restart`
   - `vault_sync`
3. **Evidence exists**: every path in `evidence_refs` points to a real file
4. **No shell commands**: the request must NOT contain shell snippets, raw commands, or feasibility language presented as implementation
5. **Sequence is valid**: sequence numbers form a valid execution order

### Step 2: Risk assessment

Classify the request:

| Risk Level | Criteria | Action |
|------------|----------|--------|
| **low** | Read-only operations only (gateway_health), or snapshot operations | Auto-approve, notify operator |
| **medium** | Config deployment + gateway restart with rollback plan | Require operator approval via Feishu |
| **high** | Security boundary changes, irreversible operations | ALWAYS require operator approval, present detailed plan |

If `requires_operator_approval` is true in the request, ALWAYS require operator approval regardless of risk level.

### Step 3: Operator approval (if required)

Present to operator via Feishu:

```
📋 Host Change Request: <task_id>

Risk: <risk_level>
Operations: <count> steps

<for each requested_host_op>
  Step <sequence>: <action> — <justification>
</for>

Evidence: <list evidence_refs>

Rollback: <first op's rollback_note>

Approve this change? (yes/no)
```

Wait for explicit "yes" before proceeding.

### Step 4: Execute via broker

Execute operations **in sequence order** using the `broker` skill:

```
For each op in requested_host_ops (sorted by sequence):
  1. Call host_ops(action: op.action, inputs: op.inputs)
  2. Check result
  3. If failed:
     - Execute rollback_note if present
     - STOP remaining operations
     - Report failure to operator
  4. If success: continue to next op
```

### Step 5: Report results

After all operations complete (or fail):

1. Report to operator:
   - Which operations succeeded/failed
   - Final system state
   - Any follow-up needed (from request's `handoff` field)

2. Update the task's `summary.json` if accessible

## Safety rules

- NEVER execute operations without reviewing the full request first
- NEVER skip operator approval for high-risk or explicitly-approval-required changes
- ALWAYS ensure a `snapshot_pre` is in the sequence before any config/restart operations
- If the request is missing `snapshot_pre`, ADD IT before executing (risk: medium or higher)
- If any operation fails, STOP and report — do not continue to subsequent operations
- NEVER invent operations not present in the request

## Example

task-runner produces:
```json
{
  "task_id": "20260401-plugin-deployment",
  "requested_host_ops": [
    { "sequence": 1, "action": "snapshot_pre", "inputs": { "label": "pre-plugin-deploy", "reason": "Before plugin deployment" }, "justification": "Safety snapshot" },
    { "sequence": 2, "action": "gateway_health", "inputs": {}, "justification": "Verify gateway is healthy before changes" },
    { "sequence": 3, "action": "deploy_openclaw_json_candidate", "inputs": { "candidate_path": "/path/to/candidate.json5" }, "justification": "Add new plugin to config" },
    { "sequence": 4, "action": "gateway_restart", "inputs": {}, "justification": "Apply config changes" },
    { "sequence": 5, "action": "gateway_health", "inputs": {}, "justification": "Verify gateway healthy after restart" },
    { "sequence": 6, "action": "snapshot_post", "inputs": { "label": "post-plugin-deploy", "reason": "After successful plugin deployment" }, "justification": "Record known-good state" }
  ],
  "requires_operator_approval": true,
  "risk_level": "medium"
}
```

main reviews → presents to operator → operator approves → executes steps 1-6 → reports.
